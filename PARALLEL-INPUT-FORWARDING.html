A bot in a sandbox: parallel input a game actually receives

An AI on your main desktop drives Minecraft running in a VM or a separate session — through a synthetic input channel, not the game's API. Your real keyboard and mouse stay yours; the two input streams never collide.

§1

The two-sided architecture

The real requirement is not "hidden vs visible" — it is a parallel, isolated input channel the user's own input never touches, feeding a game that reads hardware-level input. That splits the system across an isolation boundary.

Host (your main desktop): a process tracker that captures the sandbox's frames (pixels only, no app API) and an AI system that turns state into actions. Sandbox (VM guest or separate session): the target game and a process companion that injects real input. They close a loop: capture → decide → inject → render → capture.

§2

Why a Win32 desktop object is the wrong tool

My first pass proposed a hidden Win32 desktop object (HDESK). It cannot meet this requirement, for two independent reasons.

No parallelism. One session has a single kernel Raw Input Thread and, at any instant, one "input desktop." Hardware input and SendInput route only there; SwitchDesktop is a mutually-exclusive full switch. Two desktops cannot carry two live input streams — they collide.

Games read below the message queue. A background desktop can only be fed by PostMessage, but games read Raw Input, DirectInput, and GetAsyncKeyState — all blind to posted messages. The requirement is met one level up: a separate session or a VM.

Rejected  HDESK fails both hard requirements. It remains useful for message-driven line-of-business apps and as a window-message security boundary — neither of which is this problem. The full desktop-object analysis →
§3

What input a game actually receives

Where an injection method enters the Windows input stack decides which read paths a game can observe. It is a strict ranking:

PostMessage (window messages) < in-session SendInput < real / virtual HID device
Minecraft specifics  Java Minecraft's keyboard/menus are driven fine by in-session SendInput. But its default Raw Input ON look-motion arrives as WM_INPUT relative deltas that SendInput can't correctly produce — so in-game aiming needs a virtual/kernel HID (or toggling Raw Input off for the cursor-warp fallback).
§4

Which sandbox boundary

Four candidate boundaries, scored against the two hard requirements — parallel input, and input the game actually reads.

Trade-off  A separate session is lighter but bounded by client-Windows' single-console limit and disconnected-session render/lock problems. A VM is heavier (guest OS, GPU, capture/encode latency) but gives a clean, separate device stack — the most robust path.
§5

The closed loop & its latency

Everything is a soft-real-time loop with no in-band acknowledgement — the only feedback that an action registered is the next captured frame. The action lands k frames later, stale by the loop latency, which the policy must model (action-repeat / latency-aware training).

The dominant cost is GPU→CPU readback and cross-isolation transfer, plus policy inference — not the input injection. A small CNN fits a 60 fps budget; a large VLM does not and forces frame-skip.

§6

Corrections the verification pass caught

Adversarial fact-checking against vendor docs sharpened several load-bearing details.

SendInput vs Raw Input

SendInput does surface in WM_INPUT — but flagged. hDevice==NULL, IMO_INJECTED, and relative deltas are unreliable, so raw-input look-motion needs a real/virtual HID.

exclusive DirectInput isn't the bypass

Modern DirectInput rides on Raw Input, so it does see in-session SendInput. PostMessage is ineffective against DirectInput at all cooperative levels — the true bypass is a kernel/HID-direct read.

GetKeyState ≠ GetAsyncKeyState

Two distinct tables. SendInput moves both; PostMessage moves neither. A game polling GetAsyncKeyState is unreachable by window messages.

SendInput scope

Bound to the caller's session/desktop and UIPI — it cannot cross a session, a desktop object, or a VM guest. The injector must live inside the sandbox.

separate-session friction

Client Windows allows one active console session; a disconnected RDP session locks and stops rendering (black capture) unless you redirect with tscon + a virtual display + RDS GPU policy.

VM virtual-HID limits

Device-level input reaches everything, but absolute-coordinate mice break relative mouselook, the device is still fingerprintable, and VirtualBox has no VBoxManage mouse CLI (mouse goes through IMouse COM).

capture is isolation-bound

DXGI Desktop Duplication is session-scoped and can't reach across from the host; a VM needs an in-guest capturer (Hyper-V has no low-latency host framebuffer API).

no ACK — off-by-k

Input is one-way; the only feedback is the next frame. Frame pacing must be event-driven and de-duplicated, and the policy must model the delay — not assume synchronous step semantics.
