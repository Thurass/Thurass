Creating a hidden desktop, and forwarding input into it

A forwarder process captures input on the user's real desktop; a companion agent living on a hidden Win32 desktop object replays it against the windows hosted there. Six diagrams trace how — and where the OS says no.

§1

Three things called "virtual desktop"

On Windows 11 the phrase collapses three unrelated mechanisms at three layers. Picking the wrong one makes the goal — forward input into an isolated desktop — impossible.

Task View desktops (Win+Tab) are a shell veneer: every window still lives on the one WinSta0\Default desktop and shares its single input queue, so there is nothing separate to forward to. A separate WTS/RDP session gives real parallel input but needs a privileged Session-0 broker. A Win32 desktop object (HDESK) is the lowest-privilege thing that yields a genuine, separately addressable input queue — no service, driver, or hypervisor.

Not a sandbox  An HDESK isolates USER objects — window handles, messages, hooks — and nothing else. Token, files, registry, kernel objects, and the clipboard stay shared. It is a UI-containment primitive, not security isolation.
§2

The crux: one input desktop per session

Everything bends around one invariant. On the interactive WinSta0, at most one desktop is the input desktop at any instant — the one that is visible and receives hardware input. SwitchDesktop chooses it.

Synthesized input from SendInput / keybd_event / mouse_event lands on the input desktop too. So a hidden desktop receives neither hardware nor useful synthesized input while it stays hidden. That forks the whole design into two injection modes.

Myth, corrected  Injecting from a thread bound to a non-input desktop does not fail with ERROR_ACCESS_DENIED. The call "succeeds"; the input simply lands on a queue nobody is watching. There is no access-denied signal to detect — you architect around it, you don't catch it.
§3

Topology: two processes, one transport

Window messages and hooks are desktop-bound — "messages can be sent only between processes on the same desktop." So the forwarder→agent channel cannot ride USER objects; it must be kernel objects, which are not desktop-bound.

A pagefile-backed shared-memory ring plus an auto-reset event carries the high-rate keystroke stream (the LL-hook callback must never block); a message-mode named pipe carries framed control. Both resolve within one session across both desktops — the section/event via Local\, the pipe via \Device\NamedPipe.

§4

Injection: Mode A vs Mode B

Neither mode is a superset of the other — the choice is a real trade-off.

Mode A · concurrent

Synthetic messages

  • Agent stays on the hidden desktop; user keeps working
  • PostMessage / SendMessageTimeout to leaf HWNDs
  • Blind to Raw Input, DirectInput, GetAsyncKeyState
  • UIPI silently drops lower→higher-integrity posts
Mode B · screen-stealing

SwitchDesktop + SendInput

  • Real hardware-level input — games / anti-cheat see it
  • Makes the sandbox visible; user is locked out
  • Secure desktop can deny the switch, or "succeed" without switching
  • Orphan risk on crash → needs a watchdog with its own handle
§5

End-to-end: one keystroke's journey

A single keypress crosses one desktop boundary inside the session: captured by the low-level hook, published into the lock-free ring with a release store, consumed by the agent, decoded, and posted as WM_KEYDOWN/WM_CHAR/WM_KEYUP against the target window.

§6

Lifecycle & the teardown that never orphans

A desktop object lives while any handle, thread, or window references it. The load-bearing hazard is never leaving the user on the hidden desktop: teardown restores the captured input desktop first, drains hosted apps, detaches helper threads, then closes the last handle — in strict reverse order of creation.

⚠ CreateDesktopEx  The docs say it "assigns the desktop to the calling thread," but the running thread is not switched. A separate SetThreadDesktop is required — and it fails ERROR_BUSY if that thread already owns a window or hook. Bind first, on a fresh thread, before creating any UI.
§7

Corrections the verification pass caught

A first-pass mental model gets several Win32 details subtly wrong. These were surfaced by adversarial fact-checking against Microsoft documentation and folded into the schematic.

named pipes ≠ BaseNamedObjects

Sections and events resolve in the per-session Local\ namespace, but a named pipe is not a BNO object — it lives in \Device\NamedPipe as \\.\pipe\name. Both still work cross-desktop in one session.

cross-desktop PostMessage

You cannot reliably message a window on another desktop. The injector thread must be attached to the sandbox desktop (SetThreadDesktop) — messages travel only between same-desktop processes.

SwitchDesktop return value

A success return does not guarantee the switch happened. On a locked station it can return nonzero while the secure desktop keeps input. Verify by re-reading the input desktop's UOI_NAME.

LL-hook timeout

The "300 ms" default is folklore. Win10 1709+ hard-caps the effective LowLevelHooksTimeout at 1000 ms; an over-budget callback is passed through and the hook can be silently removed.

mouse message coordinates

WM_MOUSEMOVE and all WM_*BUTTON* carry client coordinates; only WM_MOUSEWHEEL/HWHEEL use screen coordinates. Mixing them mislocates every click.

extended-key scan code

MapVirtualKey(vk, MAPVK_VK_TO_VSC) strips the extended bit for the nav cluster and VK_RETURN. Set lParam bit 24 yourself or use MAPVK_VK_TO_VSC_EX.

CloseDesktop failure

It does not fail because a window references the desktop. Cross-process, it succeeds but the desktop persists via other references. The window/hook rule belongs to SetThreadDesktop.

WinSta0 is per-session

Not a single global object. Every console and RDP session has its own interactive WinSta0; Session 0's is headless. Target the interactive station of the specific user session.
